# 为什么把“确认”放在产品流程里

MVP Baseline Builder 面向只有一个模糊产品想法的个人构建者。这个项目关注的是开始开发之前的一段工作：把想法中的空白、相互影响的规则和必要的验收要求整理清楚，最后由使用者确认一份完整产品基线。

下面用仓库里的隔离示例解释设计。场景是假设，不是用户访谈结论；画面中的 AI 输出是预制样例，不代表模型质量评测。项目采用 AI 辅助开发，产品约束、代码和验证共同参与了迭代。

## 更适合谁来用

我想服务的是准备借助 AI 做第一个小产品的个人构建者。他可能还没有写需求文档的习惯，但已经有一个具体的设想，比如“学习时离席要扣心”。困难往往出现在下一步：哪些规则还没定？两句话同时成立时怎么办？AI 给出的补充是不是自己真正想要的？

因此，入口允许先用自己的话描述，功能清单需要本人确认，后续问题围绕产品行为展开。“暂不确定”可以留下来；等决定清楚，再一起确认完整版本。这些选择，希望减少从模糊想法直接跳到代码时，规则被随手补齐的情况。

它也适合正在给已有小产品增加一个功能、担心新规则影响旧规则的人。独立草稿让人可以先看新旧关系，读完完整预览后再提交下一版；尚未提交时，上一版仍然有效。

同方向工具服务的工作阶段各有侧重。[ChatPRD 的官方介绍](https://www.chatprd.ai/)覆盖产品文档、产品辅导和团队工具连接；[GitHub Spec Kit 的官方文档](https://github.com/github/spec-kit/blob/main/docs/index.md)把规格、计划和实现接入开发工作流。根据这些介绍，我把本项目的侧重点放在个人构建者进入开发前的规则确认，以及之后小范围新增功能时的基线延续。这是对使用场景的定位，不是完整竞品测评，也不代表其他工具没有确认或审查能力。

对于已经有成熟需求管理流程的团队，或者主要想让工具直接生成代码的人，这个项目能提供的帮助较有限。目前的人群判断来自我的设计假设，尚未通过用户访谈或规模化使用验证。

## 从“离席扣心”到可以实现的规则

“离席会扣心，短暂离席可以免罚”听起来很容易理解。但一旦开始实现，就会遇到问题：连续多久算离席？中断后重新计时吗？正常监督与免罚是否处于同一个状态？

如果 AI 直接填上数字，得到的文档会很完整，却可能不是用户想做的产品。因此，入口只要求自然语言描述，先整理整体产品设定和初始功能。用户确认清单后，功能获得稳定的 P0 编号；之后的 AI 整理不能静默删除、合并或换掉这些功能。

我希望使用者回答的是产品行为，而不是依次填写数据库字段。描述、用户意图、生效条件、核心规则和验证要求保存在结构化数据里，界面则围绕同一业务决定集中提问。

## 一个建议，什么时候成为产品规则

例子中的两条规则在同一状态下会冲突：连续离席超过 10 秒要扣心，60 秒以内又不扣心。AI 可以提出“进入独立的临时离席状态”等解决方案，但提出方案不等于使用者同意改变规则。

应用把建议单独保存。使用者先选择，再阅读确认汇总；涉及规则变更时，界面展示当前字段与接受后的字段。后端核验当前修订号、问题和关联建议，明确接受后才应用。

“暂不确定”和自定义意图都保留。“先按你觉得合理的来”也不能代替确认一份具体规则。这会让流程多一次停顿，但避免把 AI 的补全误记成用户的产品决定。

## 四项审查各自回答什么

| 审查 | 要检查的问题 |
| --- | --- |
| 清晰度 | 功能行为是否足够明确，能否知道要实现什么？ |
| 边界 | 在什么状态或条件下生效，中断与核心边界如何处理？ |
| 直接一致性 | 同一生效状态、事件或条件下，是否要求不兼容的结果？ |
| 可验证性 | 是否有适合这个功能的验证过程与预期结果？ |

四项分别记录状态和依据，通常由同一次完整请求产生。模型负责语义判断，后端负责结构和状态保护；它们不是四次独立推理，也不能保证发现所有自然语言冲突。

验证要求保存的是开发前应该怎样检查。摄像头识别等涉及真实体验的部分，需要真人参与；模拟输入适合程序逻辑，不等于已经完成真人实测。没有用户提出的指标要求时，不为了让文档显得严谨而增加误报率、样本量或统计门槛。

## 修改了需求，为什么不能沿用旧审查

一份审查只能对应某个修订。规则、答复或已接受例外变化后，修订号递增，旧审查、预览和确认失效。迟到的结果不能覆盖新草稿，失败也不能清除刚保存的答复。

问题另存为台账。模型下一轮没有提到某题，不代表问题已经解决；关闭时必须引用后续用户证据，且不能早于该题最新答复。引用出处和先后关系可以由程序检查，引用内容是否真的充分仍依赖模型和用户。

完整审查和问题台账都满足条件后，才允许最终预览。使用者阅读全部产品内容、勾选确认、主动提交，保存只读 Baseline v1。复制给开发 Agent 使用已保存原文，不重新推理或补充规则。

新增功能建立独立草稿。先确认归属，再处理新旧关系，最后对完整产品重新审查。旧基线在新版本提交前继续有效，提交后仍保留历史快照。

## 一次重复提问暴露的问题

实际使用中出现过两题：一题要求确认行为判据，另一题再次询问生效条件和中断处理。看起来是两个审查类别，实际上依赖同一个业务决定。后端当时按单个 Gate 检查缺口，自动拼出了第二题。

另一次失败发生在关闭证据上：已经重新提交的答复，不能被更早的答案覆盖。这个保护有必要，但模型没有足够明确的逐题引用约束，界面也没有说明具体是哪题出错。

修复时保留了最新答复保护，调整了三个地方：

- 一题通过 `coveredGates` 关联相关审查项；缺少关联时拒绝整轮结果，不机械补题。
- 已有重复题由用户选择主问题并重新确认答案，事务合并，保留原题、旧答复和创建依据。合并本身不修改产品字段，也不使草稿通过审查。
- 模型收到每题最新答复及允许引用的消息 ID；错误指出具体问题，说明答复已保存、本轮未应用。没有通过调整消息顺序或放宽时间判断掩盖错误。

隔离回归覆盖了相同答案重复提交、旧 A 不能覆盖后来 C、同批不同问题的先后保护，以及合并失败整批回滚。修复说明和证据见[验证记录](../VALIDATION.md)。这些机制通过不代表模型一定能识别所有同义问题。

## 目前能证明什么

源码包含单元、API、存储和浏览器回归，覆盖确认、事务、修订、问题保留、只读快照及新增版本。另有带日期的有限真实模型调查，保留成功、失败和未验证项。

目前没有用户访谈、使用规模或上线业务指标，可以证明的主要是应用机制和有限样例表现。自然语言忠实性、选项是否完整、冲突是否遗漏，还需要更多实际使用与内容复核。

后续是否真的帮助个人构建者减少返工，需要在实际使用中继续观察。
